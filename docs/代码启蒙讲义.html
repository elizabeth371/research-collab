第 0 课 · 电脑和程序，其实是一个厨房

小朋友，我们先来回答一个最笨的问题：电脑到底是什么？

你可以把电脑想象成一间很听话、但很笨的厨房：

  • 电脑里的零件（CPU、内存），就像厨房里的灶台、锅、冰箱——它们什么都不会自己干，等着有人指挥；
  • 程序（Program），就是一份菜谱——上面写着一步一步要做什么："先放油，再放菜，炒三分钟"；
  • 代码（Code），就是写下来的菜谱文字。你现在看到的所有 .py、.ts 文件，都是菜谱；
  • 运行（Run），就是照着菜谱开始做菜。
🏠 一个故事：从前有一台电脑，它什么都不会。有人给它写了一份菜谱："如果看见数字 5，就把它变成数字 6。"电脑就照着做，一遍又一遍，从来不累，也从来不问"为什么"。电脑就是这么笨——你说什么它做什么，你写错了它也跟着错。所以写代码的人一定要写得清清楚楚。
🤔 为什么学编程要先懂这个？因为后面所有代码，你都可以问自己一句话："电脑看到这一行，会照着做什么？"——这个问题能解答 90% 的疑惑。
这一课要学会的 5 个词（都会反复出现）：
· 程序 = 一份完整的菜谱（一个软件）
· 代码 = 菜谱的文字（写在文件里）
· 运行 = 照着菜谱做
· 变量 = 一个贴了名字的盒子（装东西用）
· 函数 = 菜谱里的一小段"万能步骤"（后面细讲）

第 1 课 · 你的系统 = 一家"科研小餐厅"（最重要的框架）

现在我们要给整个系统搭一个"大骨架"。这是全书最重要的一课，请慢慢读。

1.1 一个网站，分成"看得见的"和"看不见的"

你打开任何一个网站（比如淘宝），其实有两个世界同时存在：

  • 你看得见的世界（前端 Frontend）：网页长什么样、按钮点下去有什么反应。它住在你的浏览器里。
  • 你看不见的世界（后端 Backend）：数据存在哪、怎么算、怎么防作弊。它住在另一台电脑（服务器）上。

为什么一定要分开？因为你的浏览器很"透明"——任何人按 F12 都能看到网页的全部代码。如果把"我的密码怎么验证""我的数据库在哪"也写进网页，等于把保险柜钥匙贴在大门上。所以秘密都必须放后端，前端只能"喊话"让后端办事。

1.2 用"餐厅"来记住整个框架

🍽️ 你的系统是一家"科研小餐厅"：
· 你 = 客人，来吃饭（打开网页）；
· 网页（前端） = 前台，客人能看到菜单、能点菜；
· 后端 = 厨房，客人看不见，但真正的活都在这里干；
· 数据库 = 仓库，所有菜和材料（数据）都存在里面；
· HTTP（普通请求） = 传菜员，客人点一次菜，端一次菜（问一句，答一句）；
· WebSocket（长连接） = 电话线，一直通着，随时说话（打字实时同步）；
· Agent（三个小帮手） = 厨房里的研究员、作家、导师，帮你查资料、写文章、检查格式。
❓ 为什么要用餐厅来记？因为"框架逻辑"这种东西，用术语记很容易忘，用故事记一辈子忘不了。以后你看到"前端"两个字，就在心里说"哦，前台"；看到"后端"，就说"哦，厨房"。

1.3 前后端怎么说话？（传菜员和电话线）

  • 传菜员 HTTP：前端说"我要看文档列表" → 后端把列表送过来 → 结束。每次都要重新喊。适合"偶尔要一次"的事（打开页面、保存文档、检测水印）；
  • 电话线 WebSocket：一次接通，一直保持。A 打一个字，电话线立刻告诉 B。适合"随时都要同步"的事（多人协同编辑）。
🤔 为什么协同编辑必须用电话线，不能用传菜员？想象你每打一个字都要"点一次菜、等菜端上来"，打字就会卡顿 0.5 秒，体验极差。电话线一次接通后免费无限聊天，才够快。

1.4 你的"科研小餐厅"有三样独门绝活

绝活餐厅里的说法技术名字管什么用
1好几个客人同时在一张纸上写字，谁都能看到谁在写Yjs 实时协同编辑多人一起写论文
2给每道菜盖一个"防伪章"，谁要是偷改菜谱，章就会断掉SHA-256 哈希链溯源保证内容没被篡改
3给"AI 厨师"做的菜盖一个隐形印章，能检测出这菜是不是 AI 做的Kirchenbauer 水印检测 AI 生成内容

记住这句话，这就是整个系统的一句话总结：

💡 智溯系统 = 多人实时一起写论文（协同） + 谁能改、改没改，全有记录（溯源） + 是不是 AI 写的，能查出来（水印）

第 2 课 · 语言是什么？为什么有好几种编程语言

电脑是外国人，它只懂一种语言：0 和 1。我们写代码，需要"翻译"。不同的编程语言，就是不同的"翻译方式"。

2.1 四种语言，就像四种人

语言像哪种人特点
C++一个特别严格的老师每句话都要说得清清楚楚（变量是整数还是小数，必须写明白），说得清楚所以跑得快。你学过一点。
Python一个随和的朋友说话随意，不用提前声明"我要放整数还是小数"，写起来快。你的后端用它。
JavaScript一个自由的小孩浏览器里唯一的语言，很随意，有时候随意过头会出奇怪问题。
TypeScriptJavaScript 的"哥哥"在 JavaScript 基础上加了"检查"：写错了类型，还没运行就先提醒你。你的前端用它。

2.2 两个最重要的对比：翻译方式和类型检查

对比一：先翻译好，还是边做边翻译？

  • C++（编译型）：把整本菜谱先翻译成"机器语言"（生成一个 .exe 文件），再开始做。速度快，但改一行要重新翻译；
  • Python / JS（解释型）：一边读菜谱一边做，改一行立刻生效，方便，但慢一点。

对比二：盒子要不要提前贴标签？

  • C++（静态类型）：`int x = 5;` —— 提前声明"这个盒子专门放整数"。严格，不容易错；
  • Python（动态类型）：`x = 5` —— 盒子随便放，方便但容易"放错东西"；
  • TypeScript（带检查的动态）：还是随便放，但写的时候有"安检员"盯着：你要是把字符串当成数字用，它马上举红旗。
🤔 为什么你的项目选 Python + TypeScript？后端要快速开发、要用 AI 生态（Python 最强），所以用 Python；前端要多人协作、代码量不小，怕出错，所以用"有安检员"的 TypeScript。这是现在非常主流的选择。

第 3 课 · Python 语法幼儿园版（玩具盒篇）

这一课，我们把 Python 最重要的语法，用"玩具盒"的方式全学会。学完这一课，你就能读懂后端 80% 的代码了。

3.1 变量 = 贴了名字的盒子

APP_NAME = "Research Colab Backend"   # 一个盒子，名字叫 APP_NAME，里面装文字
DEBUG = True                          # 一个盒子，装"真/假"
count = 3                             # 一个盒子，装数字 3
  • = 不是数学里的"等于"，而是"把右边的东西放进左边的盒子"！这是新手最容易搞错的：Python 里判断"是否相等"用 ==（两个等号）；
  • 盒子里能装：文字（字符串 str）、数字（整数 int / 小数 float）、真/假（布尔 bool）、还有下面几种"大盒子"。

3.2 列表 = 排队；字典 = 电话本

# 列表（排队）：有顺序，第 0 个、第 1 个…
CORS_ORIGINS = ["http://localhost:5173", "http://127.0.0.1:5173"]
CORS_ORIGINS[0]        # 取第 1 个 → "http://localhost:5173"（注意从 0 开始数！）

# 字典（电话本）：按"名字"找"号码"，键→值
result = {"status": "ok", "version": "0.1.0"}
result["status"]       # 查"status"这一行 → "ok"
⚠️ 从 0 开始数，是程序员世界的规矩（C++ 也这样）。第一次总是别扭，习惯就好。

3.3 如果……就……（if 判断）

if stats["chars"] < 100:      # 如果字数小于 100
    print("太短了")         #    就打印"太短了"（注意前面有缩进！）
elif stats["chars"] < 300:  # 或者字数小于 300
    print("有点短")
else:                      # 否则（都不满足）
    print("长度合适")
⚠️ Python 最特别的规矩：缩进就是语法！在 C++ 里缩进只是好看；在 Python 里，缩进决定"这句话属于谁"。if 下面缩进的代码才在"如果"里面。缩进错了，程序直接报错。这是新手 80% 错误的原因。

3.4 重复做（for 循环）

for item in range(5):      # 让 item 从 0 数到 4，数 5 次
    print(item)          # 每次都打印出来

for d in docs:            # 从 docs（一个列表）里一个一个拿出来
    print(d.title)       # 每拿出来一个，打印它的 title

for = "对这里面的每一个东西，都做一遍下面的事"。这是电脑最擅长的——重复一万次也不累。

3.5 函数 = 万能小步骤（榨汁机）

def 加果汁(水果):          # 定义一台"榨汁机"：名字叫加果汁，需要放一个"水果"进来
    return 水果 + "汁"    # 机器吐出"水果汁"（return = 吐出来）

加果汁("苹果")            # 用这台机器 → "苹果汁"
加果汁("橙子")            # 再用一次 → "橙子汁"
  • def 名字(材料): = 定义一台机器；return = 机器的出口；
  • 为什么要把代码装进函数？因为同样的操作要用很多次。写一次，用一百次；而且给机器起个好名字（比如 compute_hash），读代码的人一眼就懂"这里在算哈希"。

3.6 类 = 模具（批量生产同款东西）

class 小狗:
    def __init__(self, 名字):   # 造小狗时自动执行，给它起名字
        self.名字 = 名字        # self = "这只小狗自己"
    def 叫(self):             # 每只小狗都会"叫"
        print("汪汪")

小黄 = 小狗("小黄")    # 用模具造出一只叫小黄的小狗
小黄.叫()             # 小黄会叫 → "汪汪"
  • class 名字: = 定义模具；__init__ = 每次造东西时自动执行的第一步（名字带两个下划线，是 Python 的"魔法方法"）；
  • self = 说"我自己"——和 C++ 的 this 一模一样；
  • 你的代码里 class WatermarkEngine:（水印引擎）、class RoomManager:（房间管理器）都是模具。

3.7 import = 从工具箱里拿工具

import hashlib                  # 拿整个"哈希工具箱"
import numpy as np              # 拿"数学工具箱"，并叫它 np（短一点好写）
from config import settings     # 从 config 文件里，拿 settings 这个变量
from models import Document    # 从 models 文件里，拿 Document 这个模具

一个文件就是一个小工具箱。from A import B = "从 A 工具箱里拿 B 工具"。C++ 里叫 #include，意思一样。

3.8 防翻车：try / except（"试试看，不行就换路"）

try:
    import asyncpg        # 先试试：能不能装上 PostgreSQL 的工具
    engine = create_engine(...)   # 能装上，就用它连数据库
except ImportError:       # 如果失败了（没装这个工具）
    pass                  # 不报错，先跳过（pass = 什么都不做）

try = "我试试"，except = "如果翻车了怎么办"。程序不怕翻车，怕翻车后没人管直接崩溃。except 就是"安全网"。

3.9 async / await = "等的时候先干别的"（点外卖）

📱 故事：你在餐厅点了一份要等 15 分钟的菜。同步 = 你站在柜台前干瞪眼 15 分钟，什么都不能干。异步 = 你点了菜，拿个号，先玩手机，菜好了服务员喊你。await 就是"我等它，但我不占着别人"。
async def 点菜():                 # async 标记：这个函数可以"边等边干别的"
    resp = await 服务员.上菜(...)  # await：等菜，但等待期间别人也能干活
    return resp
🤔 为什么你的后端到处是 async/await？因为服务器同时要服务好多客人。如果第 1 个客人点菜（请求 arXiv）要等 15 秒，而服务器"干等"，那第 2、3、4 个客人全部卡死。用了 async，等待的时间用来服务别人，大家都不卡。

3.10 with = 自动开门关门

async with async_session_factory() as db:
    # 在这里用数据库
# 一离开这个缩进块，数据库连接自动关闭

with = "用的时候开门，用完了自动关门"。省得你忘了关（忘了关 = 资源泄漏 = 服务器慢慢变慢）。

🎉 恭喜！学完这 10 个小节，你已经掌握了 Python 的核心语法。接下来的第 4~12 课，我们就用这些知识，把你后端的每一个文件读一遍。

第 4 课 · 你的后端文件地图（谁是谁）

进厨房之前，先看厨房平面图。你的后端（backend 文件夹）里有这些文件，每个文件干一件事：

文件它是什么餐厅里的对应
main.py整个后端的"大门口"餐厅总店长，负责开门营业
config.py所有设置放这里店规手册（营业时间、菜价标准）
database.py怎么连上数据库仓库的进货通道
models.py定义"数据长什么样"仓库的登记表模板
api/ 文件夹给客人开的服务窗口前台窗口（点菜、结账）
services/ 文件夹真正的"手艺活"厨房深处的大厨（做菜）
websocket/ 文件夹实时聊天的电话线电话总机
tests/ 文件夹测试菜谱好不好吃品菜员
🤔 为什么要分这么多文件？想象把所有菜谱写在一张纸上，厨房会乱成一团。一个文件管一件事，找东西快，改东西不容易碰坏别处。这叫"模块化"。

一个最常用的"电话本"——文件之间的互相引用关系（谁找谁帮忙）：

main.py ──► api/ 文件（服务窗口）
  │             │
  └──► database.py ◄── api/ 文件
         │
         └──► models.py（登记表模板）
api/watermark.py ──► services/watermark_engine.py（水印大厨）
api/agents.py    ──► services/agent_orchestrator.py（三个小帮手的总管）
api/documents.py ──► services/oplog_chain.py（盖章记账的工具）

第 5 课 · config.py —— 餐厅的"设置中心"

打开 backend/config.py，我们一行一行看。它干的事：把所有"能调的参数"集中放在一起。

class Settings(BaseSettings):       # 一个模具，用来造"设置"对象
    APP_NAME: str = "Research Colab Backend"   # 餐厅名字
    DEBUG: bool = True                          # 试营业模式开关
    CORS_ORIGINS: List[str] = ["http://localhost:5173"]
    # 上面这行：允许哪些"别的网站"来访问我（白名单）
    DATABASE_URL: str = "postgresql+asyncpg://..."   # 仓库的地址
    WATERMARK_GAMMA: float = 0.5            # 水印的"绿名单比例"
    HASHCHAIN_SALT: str = "research-colab-oplog-salt"  # 盖章用的"秘密盐"

逐行翻译成"人话"：

  • class Settings(BaseSettings): —— 定义一个模具，用来造"设置"对象。BaseSettings 是 pydantic 这个库给的"神奇基类"，继承它之后，这个模具能自动从电脑的环境变量里读值（你不用改代码，就能换设置）；
  • APP_NAME: str = "..." —— 冒号后面 str 是"类型注解"（提醒：这个盒子装文字）；= "..." 是默认值（如果没人改，就用这个）；
  • CORS_ORIGINS 为什么要单独列白名单？浏览器有规定：A 网站不许随便偷看 B 网站的数据。你的网页在 5173 端口，后端在 8000 端口，是两个"网站"。必须在后端明确说"5173 可以访问我"，否则浏览器直接把请求拦住。这就是 CORS（跨域）。
@lru_cache
def get_settings() -> Settings:
    return Settings()

settings = get_settings()
  • @lru_cache —— 装饰器（第 2 课学过：给函数加特效）。它的特效是："算过一次就记住，以后直接给结果"。因为设置只需要读一次文件，没必要每次重新读；
  • 最后一行 settings = get_settings() —— 程序一启动就造好这个设置对象，全项目所有文件 from config import settings 都拿这同一个。
🤔 为什么要把设置单独放一个文件？想象店规写在每道菜的菜谱里：改一次营业时间，要翻遍所有菜谱。集中放一个文件，改一处，全餐厅生效。

第 6 课 · models.py —— 仓库怎么登记东西

打开 backend/models.py。这个文件定义了"数据长什么样"——相当于仓库的登记表模板：每个表有一行一列，列叫什么名、装什么类型，都在这定死。

先讲清楚一个概念——数据库和 Excel 几乎一样：

数据库概念Excel 类比你的代码里
表（Table）一个工作表documents 表
一行（Row）一行数据一篇文档
一列（Column）一列字段title 列
主键（Primary Key）行号，唯一id
外键（Foreign Key）引用别的表的行号owner_id 指向 users 表
class Document(Base):                # 定义一个模具：文档
    __tablename__ = "documents"      # 对应数据库里叫 documents 的表

    id: Mapped[uuid.UUID] = mapped_column(
        UUID_TYPE, primary_key=True, default=_gen_uuid
    )                                   # 主键：每个文档的唯一身份证号
    title: Mapped[str] = mapped_column(String(512), nullable=False)
                                        # 标题：最长 512 个字，不能空
    owner_id: Mapped[uuid.UUID] = mapped_column(
        UUID_TYPE, ForeignKey("users.id", ondelete="CASCADE")
    )                                   # 外键：这篇文档是谁的（指向 users 表）
    content: Mapped[str] = mapped_column(Text, default="")
                                        # 正文：不限长度，默认空
    watermark_status: Mapped[int] = mapped_column(SmallInteger, default=0)
                                        # 水印状态：0=没查过 1=有AI水印 2=纯人类

关键翻译：

  • class Document(Base): —— 定义一个"文档"模具。Base 是 SQLAlchemy 给所有模具的公共基类（公共父类）；
  • Mapped[类型] —— 告诉 SQLAlchemy："这一列是这种类型"；
  • primary_key=True —— 主键，唯一身份证号，不能重复；
  • ForeignKey("users.id") —— 外键，指向 users 表的 id 列。ondelete="CASCADE" = "删除用户时，他的文档也一起删"（级联，像推倒第一块积木，后面跟着倒）；
  • 为什么 id 用 UUID 而不是 1、2、3？因为多人同时创建文档时，用 1、2、3 会"撞车"（两个人都拿到 3 号）。UUID 是全球唯一的乱码编号，各造各的永远不会重复。
🤔 为什么数据库这一层这么重要？因为"数据"是一家餐厅的命根子。谁删了文档、谁改了内容，都要靠"登记表"记清楚。你系统里的"溯源链"（第 10 课）就是在这些登记表上做文章的。

第 8 课 · api 文件 —— 给客人开的服务窗口

api 文件夹里有 4 个文件，套路完全一样。我们学会一个，其他全会。先记住服务窗口的 4 步套路：

1 写网址（@router）→2 拿数据库（Depends）→3 查/改数据→4 把结果还回去 
@router.get("/documents")            # 第 1 步：客人 GET /api/documents 时
async def list_documents(db = Depends(get_db)):   # 第 2 步：领一个数据库会话
    stmt = select(Document)          # 第 3 步：说"我要查文档表"
    result = await db.execute(stmt)  # 执行查询
    return list(result.scalars().all())  # 第 4 步：把全部文档还回去

新词解释：

  • @router.get("/documents") —— 装饰器。告诉 FastAPI："当有人用 GET 方法访问 /documents 网址时，调用下面的函数"；
  • Depends(get_db) —— FastAPI 的依赖注入。意思是"FastAPI，请你帮我调用 get_db，把数据库会话塞给我"。你不需要自己创建数据库连接，框架全包了；
  • select(Document) —— SQLAlchemy 的查询语法，等价于 SQL 的 SELECT * FROM documents；
  • await —— 等查询结果（异步，第 3 课学过）。

8.1 修改文档：这里藏着"溯源链"的写入点

第 9 课 · WebSocket —— 一直打着的电话

打开 backend/websocket/document_ws.py。这是全项目最"硬核"的文件，但我们用"电话"和"暗号"就能讲明白。

9.1 先认识"字节"——电话里传的不是字，是数字

电脑之间传东西，传的不是文字，是字节（Byte）——一串 0 和 1。为了好写，通常写成两位十六进制，比如 0x00（就是 0）、0x01（就是 1）、0x02（就是 2）。

MSG_SYNC = 0        # 暗号 0：这是"同步消息"（文档内容更新）
MSG_AWARENESS = 1    # 暗号 1：这是"谁在线、光标在哪"的消息
MSG_AUTH = 2        # 暗号 2：这是"验证身份"的消息（还没用）

协议 = 双方约定的暗号规则。规则是：消息的第一个字节告诉我"这是哪种消息"。就像快递单第一格填"品类"。

9.2 房间（Room）：谁和谁在一个电话群里

class RoomManager:
    def __init__(self):
        self._connections = {}   # 一个电话本：文档ID → 这个文档的"电话群"
    async def connect(self, doc_id, ws):
        await ws.accept(subprotocol="yjs")  # 接电话，并说"我懂 yjs 暗号"
        self._connections.setdefault(doc_id, set()).add(ws)  # 拉进群
  • _connections 是字典：键 = 文档 ID，值 = 一个集合（set）。集合 = "不重复的名单"（第 3 课学过）；
  • 房间 = 正在编辑同一篇文档的所有人。消息只发给同房间的人——编辑不同文档的人互不打扰；
  • subprotocol="yjs" = 握手时说"我会用 yjs 这套暗号"。前端也是这么说的，两边对上了才能通话。

9.3 最关键的一句话：转发时排除发送者

async def broadcast_update(self, doc_id, update, exclude=None):
    for ws in self._connections.get(doc_id, set()):
        if ws is exclude:   # 如果是发送者本人
            continue          # 跳过，不转发给他
        await ws.send_bytes(update)   # 发给群里其他人
⚠️ 为什么必须跳过发送者？想象一下：A 发消息 → 服务器转发给 B → B 收到后广播"我收到了" → 服务器又转发给 A → A 又广播……会永远循环下去，变成消息风暴，把服务器累垮。所以规则必须是：谁说的，就不告诉谁。

9.4 三个暗号子类型（同步流程）

if sync_type == SYNC_STEP1:    # 新客人进群：发他的"状态向量"（我有哪些内容）
    # 服务器没存内容，回一个"空更新"：00 01 02 00 00（表示"好，你同步吧"）
elif sync_type == SYNC_STEP2:  # 客人回传补丁 → 转发给别人
elif sync_type == SYNC_UPDATE: # 日常打字 → 转发给别人

这里有一个著名的坑（代码注释里都写了）：空更新必须写成 [0x00, 0x00] 两个字节，少一个字节，对方解析就会崩溃。为什么？因为 Yjs 的规则是"先写长度，再写内容"，空内容 = 长度 0，编码出来就是两个 0。这种细节，只有踩过坑才会记得住。

第 10 课 · 哈希链 —— 给账本盖章（多米诺骨牌）

这是你的系统"防篡改"的核心。打开 backend/services/oplog_chain.py。

10.1 先学"指纹"（哈希 Hash）

哈希 = 一个"数字指纹"机器。你喂给它任何内容，它吐出一个固定长度的乱码。这个乱码有两个神奇性质：

  • 内容改一个字，指纹完全变样（比如把"我爱吃苹果"改成"我爱吃苹菓"，指纹就面目全非）；
  • 指纹算不出原内容（单向的，只能正着算，不能倒着推）。

就像人的指纹：人人都有，但极难伪造，手指沾一点灰指纹就变。

def compute_hash(prev_hash, operation, timestamp, *, salt=None):
    ts = timestamp.timestamp()        # 把时间变成数字
    op_json = json.dumps(operation, ensure_ascii=False, sort_keys=True)
    # ↑ 把操作内容变成文字，键排好序（保证同一内容永远变出同一串字）
    payload = f"{prev_hash}|{op_json}|{ts:.6f}|{salt}"
    # ↑ 把四样东西串成一根面条：上一个指纹 | 内容 | 时间 | 秘密盐
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
    # ↑ 用 SHA-256 这台"指纹机"算指纹，hexdigest = 变成 64 位乱码文字

新词：

  • sort_keys=True —— 把字典的键排序再变文字。为什么？因为字典在 Python 里顺序可能变化，同一内容如果两次顺序不同，指纹就不同——排序保证"同一内容永远算出同一指纹"；
  • 盐（salt） = 一段只有你知道的秘密调料。混进去之后，外人就算知道公式也算不出你的指纹（防伪造）；
  • f"..." —— f-string，把 {变量} 的值直接塞进文字里（第 3 课学过）。

10.2 盖章记账（链是怎么形成的）

现在把"指纹"和"记账"结合起来。每次有人修改文档，就记一笔账，并且每笔账都盖上"包含上一笔指纹"的章：

第1笔账→第2笔账→第3笔账→第4笔账

第 1 笔：指纹 = SHA256(空 + 内容1 + 时间 + 盐)
第 2 笔：指纹 = SHA256(第1笔的指纹 + 内容2 + 时间 + 盐)
第 3 笔：指纹 = SHA256(第2笔的指纹 + 内容3 + 时间 + 盐)……

看出来了吗？每一笔的指纹里，都包含了上一笔的指纹。这就是"链"。就像多米诺骨牌：

🎳 多米诺故事：有人偷偷把第 2 笔账的内容改了 → 第 2 笔的指纹变了 → 但第 3 笔的指纹是拿"旧的第 2 笔指纹"算的，对不上了 → 第 4 笔也对不上……整个链条轰然倒塌。检查的人从头算一遍，立刻发现"这里断了"。这就是防篡改的原理：想改任何一笔，必须把后面所有笔全部重算——但数据库的"指纹不能重复"规则会拦住你。

10.3 检查链条（verify_chain）

def verify_chain(entries):
    prev_hash = ""                  # 从"空指纹"开始（第一笔的上一笔是空的）
    for entry in entries:            # 一笔一笔检查
        expected = compute_hash(prev_hash, entry["operation"], entry["created_at"])
        if entry["current_hash"] != expected:   # 重算的 ≠ 账上写的
            return False              # → 有人改过！
        prev_hash = entry["current_hash"]   # 把这笔的指纹传给下一笔
    return True                       # 全部对得上 → 没问题

10.4 为什么要"锁门"（并发锁）

🚪 故事：账本规则是"每笔账的指纹都要用上一笔的指纹"。假设 A 和 B 同时来记账，两个人都先看了账本——最后一笔是"指纹5"。A 算出"指纹6"写上去，B 也算出"指纹6"写上去——两笔账指纹一样，账本规定"指纹不许重复"，B 就被拒绝了，账本还乱掉了。怎么办？给账本挂一把锁：一次只让一个人记账，记完再放下一个进来。这就是 oplog_append_lock 干的事。

第 11 课 · 水印 —— 给 AI 写的东西盖印章

打开 backend/services/watermark_engine.py。这一课用"餐厅点名"的故事讲，你一定会懂。

11.1 核心思想：AI 写的东西，会"守规矩"

🍽️ 餐厅点名故事：你是餐厅老板，想分辨"哪些菜是 AI 厨师做的"。你定了一条秘密规矩：每道菜的"下一道菜"，只能从一张"推荐名单"里选。
· AI 厨师严格遵守规矩 → 它做的套餐里，绝大多数菜都在名单里；
· 人类厨师不知道规矩，随手做 → 命中名单的比例只是"碰巧"。
现在端来一桌菜，我们数"名单里的菜"有多少：多得出奇 → 这是 AI 做的；普普通通 → 人类做的。

水印算法就是把"菜"换成"字"，把"名单"换成"绿名单"：

  • 对每个"前一个字"，用一个小公式（种子 = 大素数 × 前字的编号，再混入秘密钥匙）把"所有可能的字"洗牌，前 50%（gamma）进绿名单；
  • AI 生成文本时"偏向"选绿名单里的字（把绿名单字的分数加 2.0）；
  • 检测时：把文本逐字两两检查，数"后一个字在绿名单里"的次数；
  • 算一个统计量 z（z 越大越像 AI）；z 超过 4 → 判定 AI 生成。

11.2 代码里怎么写的

def _green_list_mask(self, prev_token, vocab_size):
    rng = self._seed_rng(prev_token)      # 用"前一个字"生成一台随机机器（同一前字→同一台）
    permutation = rng.permutation(vocab_size)  # 把所有"字"洗牌（像洗扑克牌）
    green_count = int(vocab_size * self.gamma)  # 名单要多大？50%
    mask = np.zeros(vocab_size, dtype=bool)     # 一张全是"假"的清单
    mask[permutation[:green_count]] = True      # 把洗牌后前 50% 标成"真"（进名单）
    return mask

为什么用"前一个字"当种子？因为 AI 生成每个字时都参考前面的字，检测方也能根据前面的字复现"当时 AI 用的名单"——这样双方用的是同一张名单，检测才准。种子机器是可复现的：同一个"前字"永远洗出同一副牌，所以检测方算得出来。

11.3 统计检验（z 分数）

def _compute_z_score(green_count, total, gamma):
    numer = green_count - gamma * total      # 实际命中 − 应该命中（差了多少）
    denom = math.sqrt(total * gamma * (1 - gamma))  # 正常情况下会"抖"多少
    return float(numer / denom)

想象扔硬币：正常硬币扔 100 次，正面约 50 次，但会有波动（可能 48 次）。z 分数就是问："这次的正面向上的次数，比正常波动还离谱多少？"波动 2 倍 → z=2，波动 4 倍 → z=4。AI 文本的绿名单命中远超正常波动，所以 z 很大。z > 4 就判 AI，这个 4 是论文作者建议的"4 个标准差"，相当于"这事几乎不可能是巧合"。

🤔 为什么检测之前要"去重"（bigram 去重）？因为如果文章里反复出现同一个词组（比如"长安大学"出现 100 次），而这个词组碰巧总在绿名单里，命中数会虚高，人类文章会被误判成 AI。去重规则：同一个"两个字组合"只数一次，防止重复片段作弊。这是论文里的"可靠性修正"。

12.1 流水线：查资料 → 写文章 → 查格式

12.3 小导师怎么检查（规则引擎）

第 13 课 · 网页和前端 —— 桌子上的菜单

现在我们去"餐厅前台"（前端）。先补三个基础知识，不然前端代码看不懂。

13.1 网页由三样东西组成（就像一道菜的三种原料）

原料管什么类比
HTML网页的骨架（有哪些块、段落、按钮）菜的骨架（肉、菜、盘子）
CSS网页的样子（颜色、大小、位置）菜的摆盘（好看不好看）
JavaScript (JS)网页的"动作"（点击、请求、变化）菜的味道（会不会动起来）

你的前端用的是 React——一个帮你"用代码生成网页"的工具箱。它的核心思想一句话：界面 = 数据的照片。数据一变，界面自动重拍一张。你不需要手动改网页。

13.2 React 最重要的一个概念：useState（会变的便利贴）

const [docId, setDocId] = useState<string>('');
// 翻译：造一张便利贴，名字叫 docId，现在是空文字。
// 想改它？只能通过 setDocId 来改：setDocId("abc")
// 便利贴一变，用到它的界面部分自动重画。

这就是 React 的全部魔法：你只管改数据（setDocId），界面自己更新。

13.3 useEffect（开机自动做的事）

useEffect(() => {
  fetchBootstrap()...   // 组件一上场，自动去后端要数据
}, []);                   // 第二个参数 [] = "只在第一次上场时做一次"

useEffect = "组件上场后自动做的动作"（比如问后端要数据、接电话线）。第二个参数（依赖数组）决定多久做一次：[] 只做一次；[docId] 是 docId 变了就重做；不写是每次重画都做（一般不这么写）。

13.4 浏览器三件套和 React 的关系

你写的是 TypeScript（TS）→ 构建工具把它翻译成 JavaScript → 浏览器执行 JS 去改 HTML/CSS → 你看到网页。所以 TS 只是"更好写的 JS"，最后跑的还是 JS。

第 14 课 · TypeScript 语法幼儿园版（积木篇）

前端代码里你会反复看到这些"积木"，一个一个认：

14.1 形状说明书：interface（规定对象长什么样）

interface DocSummary {        // 一张"文档摘要"的图纸
  id: string;                 // 必须有 id，是文字
  title: string;              // 必须有 title，是文字
  content: string;
  updatedAt: string;
}

好处：写错字段名，编辑器立刻画红波浪线提醒你。这就是 TS"安检员"的作用。

14.2 枚举：enum（给一堆常量起名字）

enum AgentStatus {
  IDLE = 'idle',       // 空闲
  RUNNING = 'running',  // 运行中
  COMPLETED = 'completed', // 已完成
  ERROR = 'error',     // 出错
}

不用枚举的话，你可能到处写 'running'，万一拼错成 'runing' 程序也不知道。用枚举，只能选这几个，不会错。

14.3 箭头函数（= 简写的小菜谱）

// 普通写法（像 Python 的 def）
function add(a, b) { return a + b; }
// 箭头写法（更短）
const add = (a, b) => a + b;
// 异步箭头（里面可以用 await）
const handleSave = async () => { await save(); };

14.4 解构（从盒子里一次性拿出好几样）

const { session_id: sessionId } = await triggerAgent(...);
// 翻译：触发 Agent 后返回一个对象，把它的 session_id 字段拿出来，改名叫 sessionId
// （后端叫 session_id，前端规范叫 sessionId，所以改名）

const [list, v] = await Promise.all([getProvenance(docId), verifyProvenance(docId)]);
// 翻译：两个请求一起发，都完成后，第一个结果放 list，第二个放 v

14.5 模板字符串（= Python 的 f-string）

const msg = `文档 ${docId} 已保存`;   // 反引号 + ${} 插入变量

14.6 可选链 ?.（"如果有才取"）

writerMsg?.content
// 翻译：如果 writerMsg 不是空的，才取它的 content；是空的就得到 undefined（不报错）
// 没有 ?. 的话，访问空对象会直接崩溃

15.3 lib/collab.ts —— 为什么必须有"单例缓存"

const sessions = new Map<string, CollabSession>();  // 全局电话本
export function getCollabSession(docId: string): CollabSession {
  let session = sessions.get(docId);   // 先查：这个文档的电话线接了吗？
  if (!session) {                  // 没接？
    const ydoc = new Y.Doc();      // 造一个"协同记事本"
    const provider = new WebsocketProvider(..., ydoc);  // 接一根电话线
    sessions.set(docId, session);   // 记到电话本里
  }
  return session;                  // 不管接没接，都返回这根线
}
⚠️ 为什么必须"全局只接一根线"？两个原因：① React 开发模式会故意"挂载→卸载→再挂载"组件，如果每次挂载都新建连接，会开一堆重复电话线；② 编辑器、Agent 面板、水印面板都要用同一个记事本，如果各开各的连接，不但数据不同步，还会造成"光标消息无限转发回环"（A 的话传到 B，B 又传回 A，永远循环）。所以：一根线，全页面共用。代码注释里写得很明白。

15.4 协同编辑器：一块"多人共用的黑板"

const editor = useEditor({
  extensions: [
    StarterKit.configure({ history: false }),  // 基础排版功能；关掉本地撤销（协同下会打架）
    Collaboration.configure({
      fragment: ydoc.getXmlFragment('default'),  // 把编辑器接到共享记事本上！
    }),
    CollaborationCursor.configure({ provider, user: { name: username } }),
    // ↑ 多光标：把"我的光标在哪"实时告诉别人
  ],
});

黑板的比喻：Yjs 的记事本（ydoc）就是那块共享黑板。Collaboration 扩展让编辑器"盯着"黑板：别人写了什么，黑板一变化，你的屏幕立刻更新；你写了什么，黑板也记录，并同步给别人。多光标 = 黑板上显示"谁的光标在哪个字旁边"。

15.5 为什么 AI 插入内容"必须走正门"

export function appendText(editor, ydoc, text, author) {
  if (!editor || !editor.isEditable) { ... }   // 编辑器没准备好：直接操作数据层
  editor.commands.insertContentAt(editor.state.doc.content.size, {
    type: 'paragraph',
    content: [{ type: 'text', text, marks: [{ type: 'author', attrs: { author } }] }],
  });
  // ↑ 走编辑器的"正门"插入，并贴上 author 标签（ai=蓝，human=白）
}
⚠️ 为什么不能绕过正门直接往记事本里写？因为编辑器有个"同步员"（ySyncPlugin）：一旦发现记事本被外部改动，它会用记事本内容重建整个编辑器。如果你绕过正门偷偷写，重建时你的内容会被当成"来历不明的字"丢掉。走正门（editor.commands），同步员才认账。这是本项目踩过坑后写下的教训。

15.6 自动保存（防抖 1.5 秒）

editor.on('update', () => {
  timer = window.setTimeout(() => {
    const text = getPlainText(ydoc);   // 把黑板内容变成纯文字
    updateDocument(docId, { content: text, operatorId });  // 存到后端（顺带记账）
  }, 1500);
});
🤔 为什么要等 1.5 秒？你打字很快，如果每敲一个字都保存一次，后端会累垮。策略：每次打字就重置计时器，等你停手 1.5 秒才真正保存。这叫"防抖"（Debounce），就像"等水烧开，但每次有人搅一下水就重新计时"。

第 16 课 · 完整的一天（从头到尾的故事）

现在把所有知识串成一个完整的故事。请边读边回忆前面的图。

16.1 早上：你打开网页

浏览器加载前端→main.tsx 启动→App 上场→问后端要数据（HTTP）→后端查仓库→网页摆好

同时，App 调用 getCollabSession 接了一根电话线（WebSocket）到后端。后端把它拉进"演示文档"的房间。

16.2 上午：你和同学一起写论文

你打了一个字：

你的记事本（Yjs）记下→电话线告诉后端→后端转告同学（跳过你！）→同学的记事本更新→同学屏幕出现你的字

你停手 1.5 秒 → 前端把全文通过 HTTP 存到后端 → 后端锁上门 → 把这次修改盖章记进哈希链账本 → 解锁。现在，账本上多了一笔：谁、什么时候、改了什么，指纹一串。

16.3 下午：你让三个小帮手干活

你在左栏输入"帮我查查水印算法的文献"，点"启动文献检索"：

16.4 晚上：检测水印 + 检查账本 + 导出

💡 整个系统的故事，其实就一句话：一群人在一块共享黑板上写论文（协同），每写一笔都有人盖章记账（溯源），谁要是 AI 写的能查出来（水印）。前端管黑板，后端管账本和印章，数据库是仓库。

第 17 课 · 三个看代码的口诀

最后，送你三句口诀。以后遇到任何看不懂的代码，先默念它们：

口诀一：先问"电脑会照着做什么"

每一行代码，你都可以问："电脑读到这一行，会照着做什么动作？"——变量是放东西，if 是判断，for 是重复，函数是调用机器。把代码翻译成动作，就懂了。

口诀二：先看"为什么有这个东西"，再看"它怎么写"

你的项目里每一个"奇怪"的设计，背后都有一个故事：

  • 为什么空更新是两个 0？——因为有人踩过"解析崩溃"的坑；
  • 为什么转发要跳过发送者？——因为会消息风暴；
  • 为什么 AI 插入要走正门？——因为会被同步员丢掉；
  • 为什么单例缓存？——因为 StrictMode 会重复挂载；
  • 为什么加锁记账？——因为并发会撞指纹；
  • 为什么降级三步走？——因为演示不能失败。

这些"为什么"，比代码本身更值钱。答辩时讲这些故事，评委会觉得你真懂。

口诀三：从"入口"顺着走，别乱翻

  • 后端入口：main.py（看它 include 了谁）；
  • 前端入口：main.tsx → App.tsx（看它引用了谁）；
  • 顺着"调用链"走，就像跟着服务员走一遍厨房，比乱翻文件快十倍。
⚠️ 最后一个提醒：不要试图背代码。背概念地图（哪里是入口、哪里有锁、哪里会降级、两条通道怎么分工）。概念通了，代码只是查字典。
