1. 项目速览：这是什么系统

「智溯」是一个面向科研诚信场景的多 Agent 实时协同编辑 + AIGC（AI 生成内容）可信溯源原型系统。它解决的核心问题是：在多人 + AI 协作撰写科研论文的过程中，如何让"谁写的、AI 写的还是人写的、内容有没有被篡改、是否含有 AI 水印"全程可审计、可追溯。

三大技术支柱，构成系统的"科研诚信"叙事闭环：

  • 实时协同编辑 —— Tiptap 富文本编辑器接入 Yjs CRDT（冲突无关复制数据类型），多人在线编辑同一文档零冲突收敛，多光标实时可见；
  • AI/人类作者着色 —— 每个字符携带 author 属性，AI 产出蓝色背景、人类输入白色背景，谁写的"一眼可见"；
  • 可信溯源 —— 每次编辑动作写入 OpLog 操作日志，通过 SHA-256 哈希链串联，任一历史记录被篡改整条链失效；同时内置 Kirchenbauer 绿名单水印引擎，可对文本做 AI 生成检测（论文级统计检验）。

这是一个典型的演示/原型 + 软著申报项目（见 docs/软件说明书.md），因此代码中有大量"骨架实现 + 预留接入点 + 自动降级"的设计——例如 Agent 不调用真实 LLM（规则引擎替代）、水印用字符级 tokenizer（预留 tiktoken/transformers 接入点）、数据库 PostgreSQL 未安装时自动回退 SQLite。这些"降级优先"的设计是理解本代码库的关键线索。

4. 系统架构与数据流

4.1 双通道通信模型

前端 React─HTTP REST→FastAPI /api/*→SQLAlchemy async→PG / SQLite
前端 Yjs─WebSocket /ws/{doc_id}→纯转发中继→房间内其他客户端
  • REST 通道：负责文档 CRUD、Agent 触发、水印检测、溯源链查询、文献检索等"低频、需持久化"的操作；
  • WebSocket 通道：只做实时协同编辑的增量同步，实现 y-websocket 协议，服务端不持有任何 CRDT 状态（纯转发）；
  • 两条通道的配合：编辑器内容变更 → 防抖 1.5s 后走 REST 落库（写入溯源链）；实时同步走 WS；Agent 产出经 REST 触发、由前端直接以本地事务插入 Yjs（走 WS 广播给他人）。

4.2 纯转发模式的本质

这是本项目最重要的架构决策。服务端不保存 Yjs 状态，只维护"每个文档房间的连接集合"。客户端通过 CRDT 算法自行收敛——当 A、B 同时编辑产生冲突时，Yjs 的 Y.Text/Y.XmlFragment 结构保证双方最终得到一致结果，无需服务器裁决。服务端职责被降为"消息路由器"：

async def collaborative_endpoint(websocket, doc_id):
    await room.connect(doc_id, websocket)   # 加入房间（声明 yjs subprotocol）
    while True:
        data = await websocket.receive_bytes()
        msg_type = data[0]
        if msg_type == MSG_SYNC:        # 0x00 增量更新 → 转发给其他人
            await handle_sync(websocket, doc_id, data[1:], room)
        elif msg_type == MSG_AWARENESS:  # 0x01 光标/在线 → 原样转发
            await handle_awareness(websocket, doc_id, data, room)
✅ 为什么这么设计：a) 服务端无状态 → 天然支持水平扩展、崩溃不丢状态；b) 避免在 Python 侧维护 CRDT 状态的高成本；c) 开发量小，只需正确实现协议编解码。代价是"刷新后从数据库明文快照恢复"，见第 20 节已知限制。

5.1 跨方言类型技巧（先看懂这个，后面都好懂）

# PostgreSQL 用原生 UUID，SQLite 用 CHAR(32)；JSONB↔JSON；BYTEA↔BLOB
UUID_TYPE = Uuid().with_variant(PG_UUID(as_uuid=True), "postgresql")
JSONB_TYPE = JSON().with_variant(PG_JSONB, "postgresql")
BYTEA_TYPE = LargeBinary().with_variant(PG_BYTEA, "postgresql")

SQLAlchemy 的 with_variant 让同一套模型代码在两种数据库上生成不同 DDL——这是"零配置可运行"在数据层的支撑。

6.2 database.py —— 自动回退引擎（本项目最巧妙的工程之一）

核心函数 _create_engine()：

def _create_engine():
    try:
        import asyncpg
        engine = create_async_engine(pg_url, pool_size=10,
                                       max_overflow=20, pool_pre_ping=True,
                                       connect_args={"timeout": 3})  # 3 秒快速失败
        ...
        ok = asyncio.run(_probe())        # 模块导入时真实连一次 SELECT 1
        if ok: return engine
        # 失败 → 掉进下面的 SQLite 回退分支
    except ImportError: ...
    # 回退：SQLite 文件库 + 手动开启外键约束
    engine = create_async_engine("sqlite+aiosqlite:///./research_colab.db")
    @event.listens_for(engine.sync_engine, "connect")
    def _set_sqlite_pragma(conn, _):
        cursor.execute("PRAGMA foreign_keys=ON")  # SQLite 默认不启用外键！

值得注意的三个细节：

  • 双保险回退：模块导入时探测一次；若导入时事件循环已在运行（uvicorn 场景）无法用 asyncio.run，则延迟到 init_db() 建表失败时再重建 SQLite 引擎（global engine 重新赋值）；
  • SQLite 外键陷阱：SQLite 默认 foreign_keys=OFF，必须用 event.listens_for 在每个连接建立时执行 PRAGMA，否则级联删除不生效；
  • 请求级会话：get_db() 是 FastAPI 依赖，用 async with async_session_factory() as session: yield session 保证每个请求独立会话、用完自动关闭。

7. ORM 模型层 models.py

六个模型的具体字段已在上文表格列出，这里重点讲三个"非显而易见"的设计：

7.1 User 表承担 AI 作者身份

role: Mapped[str] = mapped_column(String(32), nullable=False, default="researcher")
# CheckConstraint("role IN ('admin','researcher','collaborator','ai_agent')")

为什么：溯源链要回答"这段是 AI 写的"，那 AI 就必须在用户体系里有身份。虽然当前演示里 Agent 写日志用的是文档 owner_id，但把 ai_agent 预留为合法角色，为将来"AI 用自己的账号署名"铺路。

7.2 OpLog 的哈希链字段设计

prev_hash: Mapped[str] = mapped_column(String(64), nullable=False, default="")
current_hash: Mapped[str] = mapped_column(String(64), nullable=False, unique=True)
  • prev_hash 默认空串表示链首；
  • current_hash 加 UNIQUE 约束——同一文档两条日志哈希相同即违反约束。这个约束既是防篡改保证，也引发了并发写冲突缺陷 D1（详见第 15 节），最终用应用层锁解决。

7.3 关系与级联

Document.owner → User；Document.collaborators → User（secondary 中间表）；OpLog/WatermarkRecord → Document（ondelete=CASCADE）。注意 lazy="selectin" 用于 collaborators，避免 N+1 查询。

8.1 api/documents.py —— 文档 CRUD + 溯源日志 + 导出

核心逻辑 update_document——内容更新时自动写溯源日志：

async with oplog_append_lock(doc_id):        # ① 串行化锁（D1 修复）
    doc = await db.get(Document, doc_id)
    data = payload.model_dump(exclude_unset=True)
    operator_id = data.pop("operator_id", None) or doc.owner_id  # ② 溯源元数据剥离
    content_changed = "content" in data and data["content"] != doc.content
    for field, value in data.items(): setattr(doc, field, value)
    if content_changed:
        await _append_content_log(db, doc, operator_id, old_content, doc.content)  # ③ 写哈希链日志

_append_content_log 的要点：

  • 读该文档链尾 current_hash 作为 prev_hash；
  • 首次内容写入判定 op_type='insert'，后续修改判定 'replace'；
  • 先 db.flush() 拿到数据库时间戳，再计算 current_hash——保证校验时用同一时间戳（微妙且关键，否则哈希对不上）；
  • operation 只存元数据（长度/头部 200 字/增量），不存全文，控制体积。

9. WebSocket 协同端点 document_ws.py（协议级详解）

这是全项目工程上最容易出错、踩坑最多的文件。它实现了 y-websocket 服务端协议的"最小可用子集"。

9.1 消息协议

首字节消息类型第二字节（SYNC 子类型）说明
0x00SYNC0x00 STEP1 / 0x01 STEP2 / 0x02 UPDATECRDT 状态同步
0x01AWARENESS—光标/在线状态（多光标）
0x02AUTH—鉴权（预留，当前接受一切）

9.2 三个关键编码函数

def encode_var_uint(value):   # LEB128 变长无符号整数
    out = bytearray()
    while True:
        b = value & 0x7F; value >>= 7
        if value: out.append(b | 0x80)
        else: out.append(b); break
    return bytes(out)

def encode_var_uint8_array(payload):  # [varUint(长度), 字节...]
    return encode_var_uint(len(payload)) + payload

为什么必须用 varUint 长度前缀：Yjs 的二进制协议把 update/state vector 打包成 varUint8Array——先写一个 LEB128 编码的长度，再跟原始字节。如果直接裸发字节，接收端 lib0 会把第一个字节当成长度解析，导致解码错位。

9.3 三个必须记住的"踩坑修复"（README 明确记录）

  • 空 update 必须是 [0x00, 0x00]：delete 集与插入集长度均为 0 的编码结果。发送 [0x00]（单字节）或裸空字节都会让客户端 applyUpdate 抛 Unexpected end of array；
  • SYNC_STEP1 回复：客户端发状态向量后，纯转发服务端没有状态可回，就回一个空 update（00 01 02 00 00），客户端据此进入 synced 状态；
  • 转发必须排除发送者：SYNC_UPDATE 与 AWARENESS 都 exclude=ws，否则消息在 A→B→A 之间无限回环（意识状态时钟无限递增的消息风暴）。

9.4 RoomManager 房间管理

class RoomManager:
    def __init__(self):
        self._connections: Dict[str, Set[WebSocket]] = {}   # doc_id → 连接集合
    async def connect(self, doc_id, ws):
        await ws.accept(subprotocol="yjs")          # 声明子协议
        self._connections.setdefault(doc_id, set()).add(ws)
  • subprotocol="yjs"：客户端 WebsocketProvider 探测 ['yjs', 'ycrdt,0.4.2']，不声明会握手失败；
  • 广播时对异常连接做"剔除"（disconnect），防止死连接阻塞；
  • WS_MAX_CLIENTS_PER_DOC=64 配置项存在但未强制限制（预留）。

文件末尾还提供 broadcast_state(doc_id, update) 供 AgentOrchestrator/StreamBufferService 将来把 AI 产出实时推给房间——目前未被调用（Agent 产出由前端直接插入）。

10. 服务层（5 个核心服务）

10.1 services/oplog_chain.py —— 哈希链 + 并发锁

哈希计算：

@staticmethod
def compute_hash(prev_hash, operation, timestamp, *, salt=None):
    ts = timestamp.timestamp() if isinstance(timestamp, datetime) else float(timestamp)
    op_json = json.dumps(operation, ensure_ascii=False, sort_keys=True)  # 稳定序列化！
    payload = f"{prev_hash}|{op_json}|{ts:.6f}|{salt}"
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
  • 稳定序列化：sort_keys=True + ensure_ascii=False 保证同一 operation 在不同语言/环境序列化结果一致（否则 JSON 键序变化会导致哈希不同）；
  • 时间戳精度：{ts:.6f} 固定 6 位小数，避免浮点表示抖动；
  • salt：加盐防止彩虹表式重放攻击。

verify_chain 从空串出发逐条重算比对，链上任何篡改都会在"后继条目 prev_hash 对不上"或"重算哈希不匹配"处断裂。

并发锁（缺陷 D1 修复）——这是项目自我修复的典范：

_oplog_append_locks: Dict[str, asyncio.Lock] = {}
_oplog_append_locks_guard = threading.Lock()   # 保护字典本身的并发

def oplog_append_lock(doc_id) -> asyncio.Lock:
    key = str(doc_id)
    with _oplog_append_locks_guard:
        lock = _oplog_append_locks.get(key)
        if lock is None:
            lock = asyncio.Lock(); _oplog_append_locks[key] = lock
        return lock
⚠️ D1 缺陷背景：并发 PATCH 同一文档时，两个请求同时读到相同链尾，在相同秒内（SQLite 时间戳秒级精度）算出相同 current_hash → 违反 UNIQUE 约束 → 500 且溯源链断裂。修复方案是按 doc_id 粒度的进程内 asyncio.Lock，把"读链尾→写日志→commit"整段串行化。锁字典用 threading.Lock 保护（asyncio.Lock 在 Python 3.10+ 不再有 loop 绑定问题，可直接复用）。

11.3 lib/collab.ts —— 协同会话单例缓存（防踩坑核心）

const sessions = new Map<string, CollabSession>();

export function getCollabSession(docId: string): CollabSession {
  let session = sessions.get(docId);
  if (!session) {
    const ydoc = new Y.Doc();
    const provider = new WebsocketProvider(getWsUrl(), docId, ydoc, {
      connect: true,
      protocols: ['yjs'],          // 二进制协议，匹配后端
    });
    session = { ydoc, provider, editor: null, loaded: false };
    sessions.set(docId, session);
  }
  return session;
}

为什么必须单例（文件注释写得很清楚）：

  • StrictMode double-mount 若在组件内创建 provider，会建立重复 WebSocket 连接；
  • 编辑器、Agent 面板、水印面板共享同一 Y.Doc，若各自建 provider，服务端把 A 的 awareness 转发给 B，B 应用后重新广播——意识状态无限回环、消息风暴；
  • disposeCollabSession 由 App 切换文档时调用，防止连接泄漏；
  • HMR 时 import.meta.hot.dispose 统一销毁全部会话；开发环境暴露 window.__collab 调试钩子（含 Yjs fragment 结构只读诊断）。

11.4 lib/yjs.ts —— 作者标记与文本工具

核心约定：AUTHOR_AI='ai'（蓝）、AUTHOR_HUMAN='human'（白）。重点函数：

  • collectAuthors：递归遍历 XmlFragment，收集 delta 中所有 author 值（AI/人类内容比例统计）；
  • getAuthorFromDelta：兼容两种属性存储格式（扁平 {author:'ai'} 与 mark 对象 {author:{author:'ai'}}）——这是踩坑后的兼容处理；
  • appendText/appendAiText：必须走 editor.commands.insertContentAt 通道而不是直接操作 fragment！文件注释解释了原因：ySyncPlugin 会对 fragment 的外部变更执行 synchronize 全量回写，直接插入的 XmlText 内容会被丢弃；且未注册为 PM mark 的 Yjs 属性（format/setAttribute）也会因属性映射失败触发同样问题。插入时用 marks: [{type:'author', attrs:{author}}]（mark 名是 'author' 而非 'ai'，否则报 "There is no mark type ai"）；
  • getPlainText：按 paragraph 提取纯文本，段落间换行——供水印检测与落库持久化使用。

12. 前端核心：CollaborativeEditor.tsx

这个文件把"协同编辑"拆成了 5 个相互配合的部分，逐一讲解：

12.1 AuthorMark —— 作者 mark 注册（缺它文本会被清空）

const AuthorMark = Mark.create({
  name: 'author',
  addAttributes() { return { author: { default: 'human' } }; },
  parseHTML() { return [{ tag: 'span[data-author]' }]; },
  renderHTML({ HTMLAttributes }) { return ['span', mergeAttributes(HTMLAttributes)]; },
});

为什么必须注册：mark 名即 Yjs 属性名（Tiptap Collaboration 约定）。若 Yjs 里存在未注册为 PM mark 的属性，ySyncPlugin 在 synchronize 全量重建时无法映射该属性，会导致文本内容被回写丢弃（实测踩坑：直接 format/setAttribute 后段落文本清空）。

12.2 AuthorHighlight —— ProseMirror Decoration 视图层着色

用 Decoration.inline(from, to, {class}) 给"带 author 属性的文本区间"加背景色 class。核心是 computeDecorations：递归收集所有 XmlText → 读取 delta → 累计全局字符偏移（globalOffset）把 Yjs 区间换算为 PM 绝对 position。触发重算的条件：tr.getMeta('external') === true || tr.docChanged（外部 CRDT 同步事件或本地文档变化）。

💡 注释明确：这是基于纯文本字符偏移的近似映射，纯段落场景精确；嵌套复杂块级结构时建议改用 Y.relativePosition（TODO）。这是"演示优先、复杂度让位"的又一例证。

  • Enter 键快捷检索。

14. 核心机制专题：协同编辑原理与全部踩坑

14.1 CRDT 为什么能"无服务器收敛"

Yjs 使用基于 Lamport 时钟 + 客户端唯一 ID 的偏序（Yjs 的 YATA 算法）：每个插入/删除操作都带 (clientId, clock)，冲突时按"先比较位置、再比较客户端 ID"的确定性规则合并。因此任意两端以任意顺序应用同一组操作，最终状态必然一致——这是协同编辑不需要中心裁决的理论基础。

14.2 握手与同步流程（对照 README 验证要点）

客户端连 /ws/{doc_id}→服务端 accept(yjs)→客户端发 SYNC_STEP1(状态向量)→服务端回空 update (00 01 02 00 00)→synced

之后每次编辑：本地 Yjs 生成增量 update → SYNC_UPDATE 广播 → 服务端转发给同房间其他人（排除发送者）→ 对方 applyUpdate → fragment.on('change') 触发 → ProseMirror 同步渲染 + AuthorHighlight 重算。

15. 核心机制专题：哈希链防篡改与并发锁（D1）

15.1 防篡改模型

entry0: prev="" cur=sha256("" | op0_json | t0 | salt)
entry1: prev=cur0 cur=sha256(cur0 | op1_json | t1 | salt)
entry2: prev=cur1 cur=sha256(cur1 | op2_json | t2 | salt) …

任何一条日志的 operation 被修改 → 该条 current_hash 重算不匹配（校验规则 ① 拦截）；即使攻击者同时重算自己的 current_hash，其后继条目的 prev_hash 也对不上（校验规则 ② 拦截）。链首 prev_hash 必须为空串，堵住"伪造链首"路径。UNIQUE 约束保证数据库层面不可能存在两条相同 current_hash。

15.2 D1 并发缺陷复盘

问题场景：两个 PATCH 同时到达 → 都读到链尾 cur1 → 同一秒内算出相同 cur2 → 第二条 INSERT 违反 UNIQUE → 500 + 链断。修复采用 doc_id 粒度的进程内 asyncio.Lock，把"读链尾→写 OpLog→commit"串行化。之所以不用数据库行锁（SELECT FOR UPDATE）或乐观锁版本号：SQLite 对并发写支持弱、且要保持跨数据库一致性——应用层锁最简单且对已存在的库无需迁移。

⚠️ 注意该锁是进程内的：多 uvicorn worker 或多实例部署时仍需改为数据库级锁（如 PostgreSQL advisory lock）——这是 README 未提及的部署注意点。

16. 核心机制专题：Kirchenbauer 水印完整数学原理

16.1 嵌入端（embed）

  1. 绿名单生成（PRF）：对前一个 token t_{i-1}，用伪随机函数 seed = hash_key × t_{i-1}（与 secret_key 的 SHA-256 摘要异或混合）作为 RNG 种子，对词表做 Fisher-Yates 洗牌（np.random.permutation），取前 gamma=50% 为绿名单 G(t_{i-1})；
  2. logits 偏置：logits_new[t] = logits[t] + delta（仅当 t ∈ G），使绿名单 token 被采样的概率系统性升高；
  3. 生成方与检测方共享 secret_key，因此检测方能复现完全相同的绿名单（test_paper_seeding_reproducible 验证）。

16.2 检测端（detect）

  1. 对文本 token 化（当前为 Unicode 码点，词表 65536）后，逐对 (prev, cur) 检查 cur ∈ G(prev)，统计绿名单命中数 green 与总对数 T；
  2. 统计检验：z = (green − gamma·T) / √(T·gamma·(1−gamma))；若文本含水印，green 显著偏高 → z 大；
  3. p = 1 − Φ(z)（用 erfc 精确计算标准正态上尾概率，不依赖 scipy）；
  4. 判定：z > 4.0（论文建议的 4-sigma）→ AI 生成；置信度 1 − p。

16.3 安全检测：ignore_repeated_bigrams

默认开启：对唯一 bigram 去重计数——每个 (prev,cur) 对只计一次。防止文本中反复出现的固定词组（如论文里重复的机构名）虚高绿名单命中率，导致人类文本被误判。对应论文 "On the Reliability of Watermarks" 的修正。

16.4 论文级忠实度

hash_key=15485863（论文官方默认素数）、种子公式、z 统计量、阈值 4.0 均与 jwkirchenbauer/lm-watermarking（Apache-2.0，许可证已声明）一致。测试 test_zscore_formula_matches_paper 直接断言公式；test_watermarked_text_detected 构造全绿名单采样文本验证检出。

💡 字符级 tokenizer 是演示闭环：真实 LLM 场景需用与生成时相同的 tokenizer（tiktoken/transformers），否则检测失效——代码中 _tokenize 注释已标明接入点。

17. 核心机制专题：AI/人类作者着色机制

Yjs 文本属性 author↔AuthorMark（PM mark）↔Decoration 视图层→.author-ai 蓝 / .author-human 白
  1. 数据层：Y.XmlText 的 author 属性携带作者身份（AI 插入带 'ai'，人类输入默认 'human'）；
  2. 桥接层：y-prosemirror 在 PM 事务内把 mark ↔ Yjs 属性双向映射（mark 名必须叫 'author'）；
  3. 视图层：AuthorHighlight 扩展监听 fragment change/docChanged，把 delta 区间换算为 PM position，挂 Decoration.inline 注入 class=author-ai；
  4. 样式层：.author-ai { background: rgba(59,130,246,.18) }（半透明蓝），.author-human 透明；装饰层不修改文档内容，纯渲染。

为什么用 Decoration 而不是直接改 DOM：Decoration 是 ProseMirror 的声明式视图层机制，随文档变化自动映射/重算，不会污染文档模型，且与协同同步天然兼容。
