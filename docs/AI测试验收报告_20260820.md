## 四、关键缺陷 D1：并发写入导致 500 且溯源链断裂（高严重度）

**现象**：并发触发 Agent 写作 / 水印检测 / 正文 `PATCH` 时，后端返回 `500 Internal Server Error`。

**后端日志证据**：
```
PATCH /api/documents/{id} 500 Internal Server Error
sqlite3.IntegrityError: UNIQUE constraint failed: op_logs.current_hash
```

**根因**：
- `op_logs.current_hash` 列存在 **UNIQUE 约束**（`models.py` / `database.py` schema）；
- 写入时 `prev_hash` 取自「当前链尾的 `current_hash`」（`api/documents.py:162`）；
- 当多个写入**并发**发生时，它们读到**相同的 `prev_hash`**，从而算出**相同的 `current_hash`**，违反 UNIQUE 约束 → 写入失败 500；
- 同时该文档哈希链从此断裂：后续日志的 `prev_hash` 与上一条 `current_hash` 不一致，`/verify` 返回 `valid:false`。

**影响范围**：系统是「实时多 Agent 协同」系统，并发写入是**核心场景**（多 Agent 同时写、用户编辑与 Agent 写作重叠）。当前实现无乐观锁 / 无串行化 / 无冲突重试，并发下既报错又破坏**版权溯源完整性**——而溯源链正是系统核心卖点。属高严重度。
*注：单用户顺序操作不受影响，故上述功能测试（TC-03~22）绝大部分通过。*

**复现路径**：对演示文档高并发发起「内容 PATCH + 水印检测 + Agent 写作」混合请求即可触发（本次测试中已复现并确认断链位置：第 46 条）。

**建议修复方向**：
1. 去除 `current_hash` 的 UNIQUE 约束，或改为 `(doc_id, seq)` 唯一；
2. 写 `op_log` 时加事务 + 行锁 / 串行化，或计算 `current_hash` 前**重新读取链尾**并失败重试；
3. 更稳妥：改用 `(doc_id, idx)` 自增序号构建链，避免「读后写」依赖 `prev_hash`。

## 五、关于「demo 文档 valid:false 矛盾」的调查结论（重要更正）

此前一度怀疑「清理后 demo `op_logs=0` 但 `/verify` 仍报 `checked=45`」是**数据库路径不一致**。本次精确复现 `/verify` 算法后确认：

1. **不存在路径不一致问题**。`backend/research_colab.db` 即为后端使用的库；用同源算法复现的结果与后端返回**完全一致**（`checked=45, broken@#46`）。
2. **「已清理 / 0 条」是假象**，源于脚本 bug：清理脚本与首版诊断脚本用**带连字符** UUID（`00000000-0000-4000-8000-0000000000a1`）作查询条件，而数据库以**无连字符**形式（`000000000000400080000000000000a1`）存储 → `DELETE`/`SELECT` 匹配 **0 行** → 误报「已清理 / 0 条」。演示文档的 `op_logs` **实际从未被清空**。
3. **现状**：演示文档现共 **69 条** `op_logs`，前 45 条有效，**第 46 条起断裂**（即并发缺陷 D1 造成的测试污染，至今未恢复）。

**结论**：断链是真实、由并发缺陷造成的测试污染；需修复或还原演示文档才能满足检查表 #16。
