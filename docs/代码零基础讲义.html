Part 0 · 编程世界观：程序 = 菜谱

先把心态放平。写程序这件事，本质上跟写菜谱没有任何区别：

准备食材（数据）→ 按步骤处理（算法/逻辑）→ 端上桌（输出结果）

你的系统就是一本巨大的菜谱集，只是"食材"是文字、用户、文献，"步骤"是存储、转发、检测，"端上桌"是网页显示。写代码 = 把步骤写成电脑能执行的文字。

几个必须认识的名词（以后到处都会遇到）：
· 程序（Program）：一份写好的、能完成任务的指令清单。
· 代码（Code）：指令清单的文本形式，就是你现在看到的这些文件。
· 运行（Run）：让电脑照着指令清单一步步执行。
· 变量（Variable）：一个"贴了标签的盒子"，盒子里装数据。`x = 5` 就是"把数字 5 放进贴了 x 标签的盒子"。
· 函数（Function）：一段"有名字的小菜谱"，可以反复调用。像榨汁机：放水果进去，出果汁。
· 类（Class）：一个"模具"。用模具能批量做出长一样的"对象"（实例）。
· 模块/文件（Module）：把相关代码放进一个文件，方便管理。一个 .py 文件就是一个 Python 模块。
· Bug（缺陷）：程序跑得不对，通常是因为某行写错了。找 bug 的过程叫"调试"（Debug）。
❓ 为什么叫"语言"？
因为电脑只懂 0 和 1（机器码）。人写的代码需要被"翻译"成机器码。不同的语言就是不同的"翻译规则"和"表达方式"。

Part 1 · 语言类型：C++ / Python / JS / TS 到底差在哪

你学过 Python 和 C++ 皮毛，那就从"你认识的"出发，把四种语言放进一张对比表——这张表是你理解整个项目的钥匙：

语言翻译方式类型检查典型用途一句话感觉
C++编译型（全部翻译好再运行）静态 + 强类型游戏、系统软件、高性能程序"写的时候必须把所有细节说清楚，很严格，但跑得快"
Python解释型（边翻译边运行）动态 + 强类型AI、后端服务、脚本、数据分析"写起来自由随意，跑得慢一点没关系"
JavaScript (JS)解释型（浏览器里直接跑）动态 + 弱类型网页交互（前端）"网页里唯一能跑的语言，很随性"
TypeScript (TS)先编译成 JS 再运行静态 + 强类型（可选）大型前端项目"给 JS 加上类型检查，写起来不容易犯错"

1.1 编译型 vs 解释型（翻译方式的区别）

  • 编译型（C++）：把整本"菜谱"一次性翻译成机器能懂的最终版（.exe 文件），再开始做菜。好处：做菜时不用再翻译，速度快。坏处：改一行菜谱要重新翻译一遍。
  • 解释型（Python / JS）：一边读菜谱一边做菜。好处：改一行立刻生效，开发快。坏处：运行时每次都翻译，慢一些。
  • TS 是特例：先"检查"一遍类型，再翻译成普通 JS 给浏览器跑。检查这步叫编译（tsc），你的项目里 `npm run build` 就是干这个的。

1.2 动态类型 vs 静态类型（"盒子"的严格程度）

回想你学过的：C++ 里写 `int x = 5;` 必须告诉电脑"这个盒子专门装整数"。这就是静态类型——盒子的类型写死。

Python 里写 `x = 5`，过一会还能写 `x = "你好"`，Python 不拦你。这就是动态类型——盒子随便装什么。方便，但也容易"你以为装的是数字，其实是个字符串"然后出错。

TypeScript 的聪明之处：它让 JS 也变得有类型。比如你代码里：

interface User {
  id: string;        // 这个字段必须是字符串
  username: string;
  role: UserRole;    // 这个字段必须是 UserRole 枚举
}

写错类型时，编译阶段就报错，而不是等网页跑起来才崩溃。这就是 TS 存在的全部意义：把错误提前暴露。

1.3 强类型 vs 弱类型

  • Python 是强类型：`"a" + 1` 会直接报错（字符串不能加数字），强迫你写 `str(1)` 转换。
  • JS 是弱类型：`"a" + 1` 会"自动"变成字符串 `"a1"`，不报错但结果常常出乎意料（JS 著名的坑）。
✅ 记住这张图：你的项目 = Python（后端服务）+ TypeScript（前端网页）。后端管"数据存哪里、怎么算"，前端管"用户看到什么、点什么"。两者通过"网络"对话（Part 9 会讲）。

3.1 backend/config.py —— 全项目的"设置中心"

这个文件干的事：集中存放所有可调参数。为什么要单独一个文件？因为"数据库地址""水印参数"这些值，如果散落在各个文件里，改一个参数要翻遍全项目；集中起来，改一处就够。

class Settings(BaseSettings):      # 继承 pydantic 的 BaseSettings
    APP_NAME: str = "Research Colab Backend"   # 应用名字，默认值
    DEBUG: bool = True                          # 调试模式开关
    CORS_ORIGINS: List[str] = ["http://localhost:5173"]  # 允许哪些网站访问后端
    DATABASE_URL: str = "postgresql+asyncpg://postgres:postgres@localhost:5432/research_colab"
    LLM_API_KEY: str = ""                        # 空字符串 = 没配，预留
    WATERMARK_GAMMA: float = 0.5              # 水印"绿名单"比例（Part 8 讲）
    HASHCHAIN_SALT: str = "research-colab-oplog-salt"  # 哈希链加盐（Part 8 讲）
  • Pydantic 是什么：一个帮你"校验数据格式"的库。继承 BaseSettings 后，它能自动从环境变量或 .env 文件读取配置——你在系统里设了 LLM_API_KEY 环境变量，它就能覆盖默认值。
  • CORS 是什么：浏览器的安全规则——"网页 A 默认不允许随便访问网页 B 的数据"。你的前端跑在 5173 端口，后端在 8000 端口，属于"两个网站"，所以必须在这里明确说"允许 5173 访问我"，否则浏览器会拦截所有请求。
@lru_cache                     # 缓存装饰器：只加载一次，之后直接返回缓存
def get_settings() -> Settings:
    return Settings()

settings = get_settings()      # 模块加载时就创建好，全项目共用这一个实例
💡 为什么要 lru_cache？ 如果每次都新建 Settings，就要反复读文件。lru_cache 保证"第一次调用后记住结果，以后直接给"。这是"单例模式"的一种实现——整个程序只有一份配置。

3.2 backend/database.py —— 连接数据库，还带"自动换路"功能

先回答一个基础问题：什么是数据库？

数据库 = 一个专门存数据的大仓库，支持"存、取、改、删、查"。你的系统用 SQLAlchemy 这个工具来操作它。SQLAlchemy 是"对象关系映射（ORM）"——让你用 Python 对象（如 Document(...)）代替写 SQL 语句来操作数据库。

# 关键函数：创建"数据库引擎"（引擎 = 通往数据库的管道）
def _create_engine():
    try:
        import asyncpg              # ① 试着加载 PostgreSQL 驱动
        engine = create_async_engine(
            pg_url,
            pool_size=10,           # 同时保持 10 条连接待命
            max_overflow=20,        # 忙时可临时最多加到 30 条
            pool_pre_ping=True,     # 用之前先"ping"一下连接是否还活着
            connect_args={"timeout": 3},  # 3 秒连不上就算失败
        )
        ...
        ok = asyncio.run(_probe())   # ② 真的连一次试试（SELECT 1）
        if ok: return engine        # 连上了，就用 PostgreSQL
    except ImportError: ...
    # ③ 走到这里 = PostgreSQL 不可用 → 换成 SQLite 文件数据库
    engine = create_async_engine("sqlite+aiosqlite:///./research_colab.db")
  • 连接池（pool）：建数据库连接很贵（像打一次长途电话），所以提前准备 10 条连接复用。类比：银行提前开好 10 个窗口，来了客户直接用，不用现场开窗口。
  • PostgreSQL vs SQLite：PostgreSQL 是"正规军"（正式服务器用）；SQLite 是"一个文件就是整个数据库"（学习/演示用）。你的项目设计成：装没装 PostgreSQL 都能跑——这就是"自动回退"的意义。
  • SQLite 的坑：SQLite 默认不检查外键关系，代码里用 event.listens_for 在每个连接建立时执行 PRAGMA foreign_keys=ON 打开它。
# FastAPI 依赖注入：每个请求自动获得一个数据库会话
async def get_db():
    async with async_session_factory() as session:
        yield session     # yield = "先把会话交给调用方用，用完再回来收尾"
💡 yield 是什么？ 普通函数 return 一次就结束；带 yield 的函数（生成器）可以"暂停——交出东西——再恢复"。这里的意思：get_db 把 session 交给接口函数用，接口函数结束后，代码回来自动关闭 session。async with ... as db: 是 FastAPI 依赖的标准写法，你在所有 API 文件里都会看到 db: AsyncSession = Depends(get_db)——Depends 就是"FastAPI 帮我调用 get_db 拿会话"。

回忆 3.2 说的 ORM：模型（Model）= 数据库里一张表的"图纸"。你定义一个 Python 类，SQLAlchemy 就照这个类建一张数据库表。

    title: Mapped[str] = mapped_column(String(512), nullable=False)

                                   # 0=没检测 1=含AI水印 2=纯人类
  • Mapped[类型]：SQLAlchemy 2.0 的新写法，告诉它"这个属性映射成什么数据库类型"；
  • 主键（Primary Key）：每条记录的唯一身份证号，不能重复；
  • 外键（Foreign Key）：指向别的表。`ondelete="CASCADE"` 意思是：删掉 users 表里的用户时，这个用户的所有文档自动一起删掉（级联删除）；
  • UUID 主键：全球唯一的随机 ID（如 3f2a1b...），而不是 1、2、3 递增。为什么？协同系统里多个客户端可能同时创建文档，用自增 ID 会撞车，UUID 各造各的也绝不会重复。你的 C++ 类比：相当于每个对象一个全局唯一编号。

Part 7 · 后端第 5 课：WebSocket 协同端点（全项目最难、最有价值的部分）

先补充概念：HTTP 和 WebSocket 有什么区别？

  • HTTP（普通接口）：像写信——你写一封（请求），对方回一封（响应），然后结束。每次都要重新"寄信"。
  • WebSocket（长连接）：像打电话——接通后一直保持，双方随时都能说话。协同编辑需要"A 打一个字，B 的屏幕立刻出现"，必须用电话（WebSocket）。

7.1 字节（Byte）与十六进制 —— 看懂协议的前提

网络上传送的是字节。一个字节是 8 个 0/1，通常用两位十六进制表示，如 0x00（= 十进制的 0）、0x01（= 1）。你的代码里：

MSG_SYNC = 0       # 0x00 表示"同步消息"
MSG_AWARENESS = 1   # 0x01 表示"光标/在线状态消息"
MSG_AUTH = 2       # 0x02 表示"鉴权消息"（预留）

协议 = 双方约定好的"暗号规则"：消息第一个字节告诉我这是什么类型的消息，后面跟具体内容。就像快递单：第一位数字是"品类"，后面是详细地址。

7.2 varUint 编码（变长整数）

def encode_var_uint(value):     # 把一个整数编码成字节
    out = bytearray()
    while True:
        b = value & 0x7F       # 取低 7 位（0x7F = 0111 1111）
        value >>= 7            # 右移 7 位（去掉已处理的 7 位）
        if value:
            out.append(b | 0x80)  # 还有剩余，加"继续"标记（最高位=1）
        else:
            out.append(b)       # 没剩余了，这是最后一个字节
            break
    return bytes(out)
💡 为什么要有"变长整数"？ 数字 0~127 只需要 1 个字节；大数字如 65536 需要 3 个字节。固定用 4 字节会浪费空间，变长编码按需分配，网络传输更省流量。&（按位与）、>>=（右移）、|（按位或）都是 C++ 里你学过的位运算——这里只是换了个用途。

7.3 完整消息流程（一次协同同步的完整故事）

客户端1连上→发 SYNC_STEP1（我的状态向量）→服务端回空 update（00 01 02 00 00）→synced 就绪
客户端1打字→发 SYNC_UPDATE（增量）→服务端转发给客户端2（跳过发送者）→客户端2应用 → 屏幕更新 
# 服务端收到 SYNC_UPDATE 后做的事：
elif sync_type == SYNC_UPDATE:
    if not payload: return
    await room.broadcast_update(
        doc_id,
        bytes([MSG_SYNC, SYNC_UPDATE]) + encode_var_uint8_array(payload),
        exclude=ws,     # 关键：不把消息传回给发送者本人！
    )
⚠️ 这里的"踩坑"值得记住：如果服务端把消息也转发回发送者，就会形成"我转发你→你收到又转发我→我又收到再转发你……"的无限循环（消息风暴）。所以必须 exclude=ws 排除发送者。另一个坑：Yjs 的"空更新"必须编码成 [0x00, 0x00]，少一个字节客户端解析就会崩溃——这些注释里都记录着血泪史。

8.1 services/oplog_chain.py —— SHA-256 哈希链（防篡改核心）

先懂哈希（Hash）：一个"数字指纹"函数。给任何内容，算出固定长度的乱码串；内容改一丁点，指纹完全变样；且无法从指纹反推内容。

def compute_hash(prev_hash, operation, timestamp, *, salt=None):
    ts = timestamp.timestamp() if isinstance(timestamp, datetime) else float(timestamp)
    op_json = json.dumps(operation, ensure_ascii=False, sort_keys=True)
    payload = f"{prev_hash}|{op_json}|{ts:.6f}|{salt}"
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()

拆解这行"指纹公式"：当前指纹 = SHA256(上一个指纹 | 操作内容 | 时间 | 盐)

  • sort_keys=True：把字典的键排序再序列化。为什么？字典在 Python 里的顺序可能变化，如果两次算哈希时键顺序不同，指纹就不同了——排序保证"同一内容永远算出同一指纹"；
  • 盐（salt）：一段保密字符串混进去，让外人即使知道公式也算不出你的指纹（防伪造）；
  • 链的威力：每条日志的指纹都"锁住"了上一条的指纹。中间任何一条被改 → 它自己的指纹变了 → 下一条的"上一个指纹"对不上 → 再下一条也对不上……整条链像多米诺骨牌一样全部倒下。校验时从头重算一遍，任何一处不匹配就报警。
def verify_chain(entries):
    prev_hash = ""                      # 从空串开始（链首约定）
    for entry in entries:
        expected = compute_hash(prev_hash, entry["operation"], entry["created_at"])
        if entry["current_hash"] != expected:  # 重算的 ≠ 存的 → 被改过！
            return False
        prev_hash = entry["current_hash"]   # 接力：下一个用它当"上一个指纹"
    return True
💡 并发锁（为什么要有）：假设 A、B 两人同时编辑。A 读到链尾是"指纹#5"，B 也读到"指纹#5"，两人同时算出"指纹#6"——数据库规定"指纹不能重复"，B 就报错，而且链乱了。解决方案：给每个文档加一把锁（asyncio.Lock），同一时间只允许一个人"读链尾→写日志→提交"，其他人排队等。这就是 oplog_append_lock(doc_id) 的由来。

8.2 services/watermark_engine.py —— Kirchenbauer 水印（用统计判断"这是不是 AI 写的"）

这个算法的思想，用一个生活故事讲：

假设你开了一家餐厅，为了知道哪些菜是"AI 厨师"做的，你定了规矩：每道菜的下一道菜，只能从"提前画好的名单"里选。AI 厨师严格照规矩做，所以 AI 做的套餐里，绝大多数菜都来自名单；人类厨师不知道规矩，随手做，命中名单的比例只是"碰巧"。

现在端上一桌菜，我们数"名单里的菜"占了多少：比例明显高于正常 → 这桌是 AI 做的；比例正常 → 人类做的。水印就是这么工作的：

  1. 绿名单生成（_green_list_mask）：对每个"前一个字符"，用种子（hash_key × 前字符 + 密钥哈希）把 65536 个"虚拟字符"洗牌，前 50%（gamma=0.5）进绿名单；
  2. 检测（detect_watermark）：把文本逐字符两两分组，数"后一个字符在前一个字符绿名单里"的次数；
  3. 统计检验：算 z 分数 z = (命中数 − 期望命中数) / 标准差，z 越大越像 AI；z > 4 判 AI 生成（4 个标准差，统计学上极显著）；
  4. 防误判：开启"bigram 去重"——同样的两字符组合只数一次，防止文本里反复出现某个词组导致误报。
def detect_watermark(self, text: str):
    tokens = self._tokenize(text)         # 把文本变成数字列表（字符→Unicode 码点）
    if len(tokens) < 2:                 # 太短没法判断
        return {"is_ai_generated": False, ...}
    stats = self._score_sequence(tokens)   # 数绿名单命中 → z 分数 → p 值
    is_ai = stats["z_score"] > self.detection_threshold  # z>4 判 AI
    confidence = round(1.0 - stats["p_value"], 6) if is_ai else 0.0
💡 为什么置信度 = 1 − p 值？ p 值是"这桌菜其实是人类做的、但被误判成 AI"的概率（越小越好）。所以 1 − p 就是"这桌确实是 AI 做的"的把握。p = 0.01 → 置信度 99%。

Part 9 · 网页是怎么工作的：HTTP / REST / JSON / 数据库 / WebSocket

前端代码看不懂，往往不是 JS 语法问题，而是不理解网页和服务器怎么协作。这一节把地基打牢。

9.1 前端、后端、浏览器、服务器的角色

你（用户）→浏览器（打开网页）→前端代码（React，管界面）→后端代码（FastAPI，管数据）→数据库
  • 浏览器：你的电脑上运行网页的地方。前端代码（HTML/CSS/JS）就在浏览器里跑；
  • 前端：决定"长什么样、点了有什么反应"；
  • 后端：决定"数据存哪、怎么算"。它跑在服务器（另一台电脑或你自己的电脑）上，前端不认识数据库，必须通过后端；
  • 前后端靠"网络请求"对话——这就是 HTTP。

9.2 HTTP 与 REST（网址 = 动词 + 名词）

HTTP 请求就是一个"快递单"：方法（动词）+ 网址（名词）。REST 风格规定：

HTTP 方法动词含义你的项目例子
GET取数据（不改变任何东西）GET /api/documents → 拿文档列表
POST新建数据POST /api/documents → 创建文档
PATCH改部分数据PATCH /api/documents/{id} → 更新正文
DELETE删除数据DELETE /api/documents/{id} → 删文档

网址里的 {doc_id} 是"路径参数"——/api/documents/abc123 就是操作 id 为 abc123 的文档。

9.3 JSON（前后端之间的"普通话"）

{ "title": "我的论文", "year": 2026, "tags": ["AI", "水印"] }

JSON 就是"用文本表示数据"的通用格式，长得跟 Python 字典几乎一样。前端把 JSON 发给后端，后端把结果转成 JSON 返回。Python 侧转换用 json.dumps（对象→文本）/ json.loads（文本→对象）；JS 侧用 JSON.stringify / JSON.parse。

9.4 数据库和 ORM 的对应关系

数据库概念Excel 类比Python ORM 写法
表（Table）工作表class Document(Base)
行（Row）一行数据Document(title="...")
列（Column）一列字段title: Mapped[str]

9.5 浏览器三件套：HTML / CSS / JavaScript

  • HTML：网页的"骨架"——<div> 是块、<p> 是段落、<button> 是按钮；
  • CSS：网页的"衣服"——颜色、大小、布局。你的项目用 TailwindCSS，把常用样式写成 className="px-3 py-1 rounded" 这样的短类名（p=内边距、rounded=圆角）；
  • JavaScript：网页的"肌肉"——让按钮能点击、数据能刷新。TS 就是"带类型检查的 JS"。
✅ React 是什么：一个"用函数生成网页"的框架。核心思想：界面 = 数据的函数。数据变了，界面自动重画。你只需要写"这个状态长这样"，不用手动改网页。

async function request<T>(path: string, options?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, {
    headers: { 'Content-Type': 'application/json' },
    ...options,
  });
  if (!res.ok) {
    throw new Error(`API ${path} 请求失败: ${res.status}`);
  }
  return await res.json();   // 把响应的 JSON 解析成对象
}
  • fetch：浏览器自带的"发 HTTP 请求"函数（像 Python 的 httpx）。await fetch(...) = 发请求并等响应；

  • ...options：展开运算符——把调用者传的额外选项（如 method、body）合并进来。相当于 Python 的 **dict。

    ? await detectDocumentWatermark(docId)   // 检测全文并留痕
    : await detectWatermark(text);           // 检测粘贴的文本
  setResult({ ...r, latencyMs: Math.round(performance.now() - started) });
  if (persist) await refreshRecords();       // 留痕后刷新历史记录
};
  • performance.now()：浏览器提供的高精度计时器，用来算"检测花了多少毫秒"；
  • { ...r, latencyMs: ... }：展开对象再加一个新字段——复制 r 的所有字段，并补充 latencyMs。

14.3 ProvenancePanel（右栏）—— 展示"操作账本"

const [list, v] = await Promise.all([
  getProvenance(docId),      // 拉取操作日志列表
  verifyProvenance(docId),   // 同时校验哈希链完整性
]);

顶部显示"✓ 链条完整"或"✗ 检测到篡改"徽标，下面按时间列出每条操作（插入/替换/水印检测...）和哈希缩略。这个面板就是哈希链的"可视化人证"。

14.4 LiteraturePanel（右栏）—— 查文献、插引用

const handleInsert = async (item) => {
  const { citation } = await getCitation(item.id);   // 后端生成 GB/T 7714 引文
  appendText(getCollabSession(docId).editor, ydoc, `【引用】${citation}`, 'human');
  // ↑ 以"人类"身份插入（引用是研究者自己插的，不算 AI 内容）
};

注意插入时作者标记用的是 'human'——这个细节体现了产品语义：AI 写的是蓝的，人类插引用是白的。

Part 15 · 终极串讲：你打一个字，系统发生了什么

把前面所有知识串成一条完整的故事线（这也是面试/答辩最常被问的）：

15.1 场景一：你打开网页

浏览器加载前端代码→App 组件启动→GET /api/bootstrap→后端查数据库→返回演示用户+文档→页面显示

15.2 场景二：两个人同时编辑（协同的核心时刻）

A 打字→本地 Yjs 生成增量→WebSocket 发给后端→后端转发给 B→B 的 Yjs 应用增量→B 屏幕出现文字

同时：A 停手 1.5 秒后 → PATCH /api/documents → 后端写哈希链日志 → 溯源链 +1 条。B 的光标位置也通过 awareness 消息实时同步给 A。

15.3 场景三：你点"启动文献检索"

前端 POST /api/agents/invoke→Orchestrator 建会话→Research 节点：抽关键词→查 arXiv→降级本地→Writer 节点：生成草稿→Supervisor 节点：格式审查→返回 session_id→前端拉消息 + AI 内容蓝字入文档

15.4 场景四：水印检测 + 导出

前端取全文→POST /watermark/documents/{id}/detect→引擎算 z 分数→z>4 → AI 生成→写水印记录+溯源日志→前端显示置信度条

导出时后端现场把整条哈希链重新算一遍，把"✅ 校验通过/❌ 被篡改"写进 Markdown 文件头——这就是"可信导出"。

✅ 如果只记一件事：实时协作走 WebSocket（快、无状态），持久化与检测走 HTTP（慢、但要落库）。这两条通道的分工贯穿整个系统。

Part 16 · 给新手的调试与学习建议

16.1 遇到看不懂的代码怎么办

  1. 先看注释和 docstring：这个项目的注释质量很高，几乎每个文件开头都解释了"这个文件干嘛的"；
  2. 从"入口"读起：后端从 main.py 开始，前端从 main.tsx → App.tsx 开始，顺着调用关系读，比乱翻文件高效得多；
  3. 用"打印法"调试：Python 里 print(变量)，JS 里 console.log(变量)，在关键位置打印，看实际值是不是你猜的——这是新手最高效的调试方式；
  4. 拆小验证：看不懂一大段，就把输入输出抄出来，在小脚本里单独跑那段逻辑。

16.2 动手实验清单（强烈推荐）

  • 把 backend/config.py 的 WATERMARK_GAMMA 改成 0.3，重启后端，看水印检测结果变化——你就理解了 gamma 的作用；
  • 在 watermark_engine.py 的 detect_watermark 里加一行 print(stats)，用"检测粘贴的文本"功能看 z_score 的实际数值；
  • 注释掉 exclude=ws，开两个标签页编辑，观察控制台消息风暴——你会永远记住"转发必须排除发送者"；
  • 手动在数据库里改一条 op_logs 的 operation 内容，再点"溯源链"面板的校验——亲眼看"检测到篡改"。

16.3 推荐的学习路径

  1. Python 基础：官方教程前 8 章（变量、容器、函数、类、文件、异常）就够读代码了；
